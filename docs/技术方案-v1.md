# 本地离线密码管理器 · 技术方案 v1

> 状态：已确认，M1 已完成（2026-10）
> 目标平台：Windows 10 1809+ / Windows 11（绿色版）
> 技术栈：C# / .NET 8（LTS）+ WinUI 3 / Windows App SDK
> 依赖前提：完全离线运行，无任何网络调用

---

## 1. 范围

### 1.1 第一版要做
密码库的创建 / 打开 / 增删改查 / 搜索 / 加密落盘 / 密码生成（独立窗口 + 输入框内）/ 剪贴板复制与自动清空 / 自动锁定 / 回收站 / 绿色版打包。

### 1.2 第一版不做
浏览器扩展、自动填表、系统热键、云同步、导入导出、密钥轮换、库合并、联网查重、多用户、macOS / Linux。

### 1.3 设计约束
| 约束 | 落实方式 |
|---|---|
| 绝对不能联网 | 不引用任何 `System.Net.*` / `Windows.Networking` 类型；无自动更新；无遥测；无崩溃上报；不调用浏览器 |
| 数据只存本地 | 只有两个文件：密码库 + 钥匙文件，路径由用户指定，不写注册表 |
| 绿色版 | 自包含发布，不安装、不需要管理员权限 |
| 单文件即整库 | 加密后整库写入一个文件，不做外部数据库 |

## 2. 技术选型与理由

| 项 | 选择 | 理由 |
|---|---|---|
| 运行时 | .NET 8（LTS） | Windows App SDK 官方支持；SDK 10 可以编译 net8 目标 |
| UI | WinUI 3 / Windows App SDK 1.7+ | 用户指定；Fluent 外观，原生 Windows |
| 架构模式 | MVVM + 分层 | Core 与 UI 解耦，加密逻辑可单元测试 |
| MVVM 工具 | CommunityToolkit.Mvvm | 源生成器，零反射，无额外依赖 |
| JSON | System.Text.Json（源生成） | 内置，可裁剪，无第三方包 |
| 加密 | .NET 内置 AES-GCM / RSA-OAEP | 平台实现，无第三方密码库 |
| 测试 | xUnit | 覆盖 Core 全部关键路径 |
| 打包 | `dotnet publish -r win-x64 --self-contained` + `WindowsAppSDKSelfContained` | 绿色文件夹，双击即用 |

**不引入的依赖**：HttpClient 相关包、Newtonsoft.Json、任何遥测 SDK、CsWin32（P/Invoke 手写，减少依赖）。

## 4. 数据模型（解密后的 JSON）

落盘的明文是一个 JSON 文档，字段设计便于以后扩展（反序列化忽略未知字段，不因旧版读不了新版而炸库）。

```jsonc
{
  "schemaVersion": 1,          // payload 结构版本
  "vaultId": "uuid",           // 库的唯一标识
  "createdUtc": "2026-01-01T00:00:00Z",
  "updatedUtc": "2026-01-01T00:00:00Z",
  "items": [
    {
      "id": "uuid",
      "title": "GitHub",                 // 必填，唯一性不强制
      "username": "alice",
      "password": "明文（整库已加密）",
      "url": "https://github.com",       // 仅文字，不提供点击打开
      "notes": "恢复码在抽屉里",
      "tags": ["工作", "开发"],
      "createdUtc": "...",
      "updatedUtc": "...",
      "deletedUtc": null                 // 非空 = 在回收站
    }
  ]
}
```

约定：
- 所有时间用 UTC ISO-8601 字符串。
- 字段上限：标题 200 字，用户名 200，密码 1000，网址 2000，备注 8000，标签 20 个 × 30 字。超限截断并提示。
- `tags` 用字符串数组，不做标签表，简化第一版。
- `passwordHistory` 预留字段，第一版不写入。

**为什么用 JSON 而不是 SQLite**：库是「一个文件、整库解密进内存」，条数在几千级时 JSON 序列化/反序列化是毫秒级；SQLite 会带来额外的原生库、文件锁、备份复杂度，与「单文件加密」目标相冲突。超过 1 万条再评估。

## 5. 钥匙文件格式

扩展名建议 `.key`，内容是 UTF-8 JSON（内嵌 Base64），不是标准 PEM —— 避免被其他工具误用，也方便带版本和指纹。

```jsonc
{
  "format": 1,
  "type": "RSAPrivateKey",
  "keyId": "9f2c41d0a7b3e588",     // 公钥 SHA-256 前 8 字节，小写 hex
  "algorithm": "RSA-3072",
  "createdUtc": "2026-01-01T00:00:00Z",
  "publicKeySpki": "base64",       // SubjectPublicKeyInfo
  "privateKeyPkcs8": "base64"      // PKCS#8，明文（用户已确认）
}
```

- 私钥是明文（已确认的取舍）。**后续可选**：PKCS#8 口令加密（v2）。
- 生成后立即落盘，并提示用户「请复制一份到别处」。
- 打开时先比对 `keyId` 与密码库头部，不一致直接报「钥匙不匹配」，不尝试解密。

## 6. 密码库文件格式

二进制，扩展名建议 `.pwdb`。

```
偏移   长度   内容
0      4    魔数 "PWDB"（ASCII）
4      2    格式版本 u16 LE，当前 1
6      4    头部长度 N u32 LE
10     N    头部 JSON（UTF-8）
10+N   4    密文长度 M u32 LE
14+N   12   AES-GCM nonce（每次保存重新随机）
26+N   M    密文
26+N+M 16   GCM 认证标签

AAD（附加认证数据）= 偏移 0 .. 14+N（魔数 + 版本 + 头部长度 + 头部 + 密文长度）
```

头部 JSON（明文，不含任何账号信息）：

```jsonc
{
  "format": 1,
  "app": "pwdmgr",
  "createdUtc": "...",
  "cipher": "AES-256-GCM",
  "wrap": "RSA-OAEP-SHA256",
  "keyId": "9f2c41d0a7b3e588",
  "keyBits": 3072,
  "wrappedKey": "base64",     // 被 RSA 包裹的 32 字节数据密钥
  "payloadSchema": 1
}
```

设计理由：
- 头部明文只暴露加密参数与钥匙指纹，不泄露条目数量、标题等任何内容。
- 密文长度会暴露「大概有多少条」，属于可接受的泄露；如需要可加填充，第一版不做。
- 版本号 + `payloadSchema` 分离，将来改结构不用改加密格式。

## 7. 加密与密钥流程

### 7.1 算法
| 用途 | 算法 | 参数 |
|---|---|---|
| 数据加密 | AES-256-GCM | 32 字节密钥，12 字节随机 nonce，16 字节标签 |
| 数据密钥包裹 | RSA-OAEP-SHA256 | RSA-3072 |
| 指纹 | SHA-256 | 取前 8 字节 |

### 7.2 创建密码库

```
1. 生成 RSA-3072 密钥对（KeyPairFactory）
2. keyId = SHA-256(SPKI)[0..8]
3. dataKey = 32 字节随机（RandomNumberGenerator）
4. wrappedKey = RSA-OAEP-SHA256(公钥, dataKey)
5. payload = 空库 JSON → UTF-8 字节
6. nonce = 12 字节随机
7. 密文+标签 = AES-256-GCM(dataKey, nonce, payload, AAD=头部)
8. 原子写密码库文件；原子写钥匙文件（先库后钥匙，失败则回滚删除）
9. 清零 dataKey 与 payload 字节
```

### 7.3 打开密码库

```
1. 读魔数/版本/长度，校验文件完整性（E100/E101/E102）
2. 读钥匙文件，校验格式（E200）与 keyId 是否等于头部（E201）
3. RSA 解 wrappedKey → dataKey；OAEP 校验失败 = 钥匙不对（E202）
4. AES-GCM 解密并校验标签；失败 = 文件被篡改/损坏（E203）
5. 反序列化 payload，检查 schemaVersion
6. 数据装入 VaultDocument（内存）；dataKey 与明文字节清零，仅保留在锁定前需要的内存模型
```

**错误区分是刻意设计的**：
- 钥匙不对 → OAEP 解包失败，立刻明确告知，不给「文件损坏」的误导。
- 钥匙对但文件被动过 → GCM 标签失败，提示用 `.bak` 恢复。
- 两种失败都不会显示任何条目。

### 7.4 保存

```
1. 序列化 payload → 字节
2. 新 nonce（随机），重新 AES-GCM 加密；wrappedKey 复用
3. 写 <库名>.tmp → Flush(true) 落盘
4. 若已有库文件：File.Replace(tmp, 库, 库.bak)（同卷）；跨卷/不支持时退化为「复制旧文件为 .bak → 覆盖写」
5. 删除 tmp
6. 读回校验（可关）：重新解析头部 + 解密 + 反序列化，失败则回滚到 .bak 并报 E300
```

要点：
- 每次保存都换 nonce；同时把上一次 nonce 记录下来，万一随机源异常重复则重新生成。
- 保存失败时原文件保持不动，`.bak` 仍可用。
- 只保存变更过的库；关闭时若存在未保存修改会先保存。

### 7.5 互斥
- 同一库文件同一时间只允许一个进程打开：库目录下 `<库名>.lock` 独占打开，进程退出时删除。
- 应用单实例（命名 Mutex）：第二次启动只激活已有窗口，避免两个窗口写同一个库。
- 读到陈旧锁文件时提示「该库正在另一个窗口打开」并提供强制打开（会提示风险）。

## 8. 内存与锁定策略

| 场景 | 行为 |
|---|---|
| 解锁后 | dataKey、密钥材料只存在内存；条目明文在 VaultDocument 中 |
| 闲置超时（默认 5 分钟，可配 1/5/15/永不） | 自动上锁，清空 VaultDocument 与 dataKey，回到解锁页 |
| 系统锁屏（WTS SessionSwitch） | 立即上锁 |
| 手动上锁 / 关闭窗口 | 立即上锁并保存 |
| 进程退出 | 所有敏感字节 `CryptographicOperations.ZeroMemory` |

已知局限（诚实说明）：.NET 的 `string` 不可清零，密码在字符串形式存在期间仍可能留在内存中；本方案只能做到「字节数组尽量清零、生命周期尽量短」，不能做到「内存中绝无明文」。

## 9. 剪贴板方案

- 复制密码/用户名时同时放入两个标记：`CanIncludeInClipboardHistory = 0`、`CanUploadToCloudClipboard = 0`（Windows 10+ 支持，用于让 Win+V 历史与云剪贴板忽略该内容）。此机制为「尽力而为」，需在目标机器实测。
- 复制后启动 30 秒计时器；到点时先比对剪贴板当前内容是否仍是我们放进去的值（SHA-256 摘要比对），是则清空，否则不动（避免清掉用户后来复制的东西）。
- 清空后不留任何提示音/气泡，避免引人注意。
- 手动「清空剪贴板」按钮放在工具栏。

## 11. 错误码与用户提示

| 码 | 含义 | 用户看到的话 |
|---|---|---|
| E100 | 不是密码库文件 | 这不是一个有效的密码库文件 |
| E101 | 版本不支持 | 这个库由更新的版本创建，请升级 |
| E102 | 文件截断/损坏 | 文件不完整，可能复制中断 |
| E103 | 找不到密码库文件 | 找不到密码库文件 |
| E104 | 目标文件已存在 | 目标文件已存在，请换一个位置或改名 |
| E200 | 钥匙文件格式错误 | 这个文件不是本软件的钥匙 |
| E201 | 钥匙与库不匹配 | 这把钥匙不属于这个库 |
| E202 | 无法解包数据密钥 | 钥匙损坏或不属于此库 |
| E203 | 解密校验失败 | 文件被修改或损坏，可尝试 .bak |
| E300 | 保存失败 | 保存失败：磁盘满/无权限/被占用 |

| E400 | 库被占用 | 这个库正在另一个窗口打开 |

## 12. 离线保证的实现与验证

实现层面：
1. 项目不引用 `System.Net.Http`、`System.Net.Sockets`、`Windows.Networking.*`。
2. 无自动更新代码、无遥测、无崩溃上报、无「检查更新」菜单。
3. 不调用 `ShellExecute` 打开网址或文件（避免间接联网/执行）。
4. 发布产物里不包含任何联网配置。

验证层面：
1. 单元测试扫描 `Core` 与 `App` 源码，出现禁用命名空间即失败（架构守护测试）。
2. 验收时断网（拔网线/关 Wi-Fi）跑完整流程：建库、增删改查、生成、复制、重启打开。
3. 用 `netstat`/资源监视器确认进程无出站连接（手工检查）。

## 13. 测试计划

### 13.1 Core 单元测试（必须）
- 加密往返：创建 → 保存 → 重新打开，条目逐字段相等。
- 错钥匙：用另一对密钥打开 → E201/E202，且不返回数据。
- 篡改：翻转密文/头部任一字节 → E203。
- 截断：文件截到各种长度 → E102，不崩溃。
- 版本：头部版本改为 99 → E101。
- 原子写：模拟写 tmp 后失败 → 原库文件不变，`.bak` 存在。
- 锁：两个 VaultStore 同时打开同一文件 → 第二个 E400。
- 生成器：长度边界、字符集覆盖、每类至少一个、排除易混字符、无偏采样（卡方近似）、熵值计算。
- 搜索：标题/用户名/网址/备注大小写不敏感；回收站条目不出现在主列表。
- 回收站：删除 → 可恢复；超 30 天清理。

### 13.2 手工验收清单
- 绿色文件夹复制到另一台机器/另一路径，双击可运行、可打开库。
- 断网全程可用。
- 剪贴板 30 秒后为空；期间复制别的内容不被误清。
- 闲置 5 分钟自动上锁；锁屏立即上锁。
- 生成器与输入框内生成结果符合勾选规则。
- 拔出 U 盘/关闭文件占用时保存失败有明确提示且原库完好。

## 18. M2 修订（用户反馈后）

### 18.1 修复：创建密码库报「密码库已存在」

现象：在创建页选好密码库与钥匙位置后点击创建，提示目标文件已存在；随后目录里确实出现了一个空的密码库文件，而钥匙文件没有。

原因：系统的「另存为」对话框会在用户确认后**立即创建一个 0 字节文件**。`VaultSession.CreateAsync` 原本只要目标路径存在就拒绝，所以这个占位文件被当成了已有库；因为异常在写钥匙之前抛出，最终只留下一个空文件。

修复：`CreateAsync` 改为 `EnsureWritableTarget`——0 字节占位文件视为可写目标，**直接覆盖写入**（不删除重建，避免文件仍被选择器持有导致 `Access denied`），写入前清除只读属性；非空文件仍然拒绝（E104），避免误覆盖已有密码库或别的数据。失败时抛出的消息会说明是“写入密码库失败”还是“已存在”，并在程序目录的 `startup.log` 里记录目标文件的存在性、长度、属性与所在目录，便于定位权限问题。新增三条单测覆盖占位文件、只读占位文件、非空文件。

### 18.2 条目直接编辑

- 详情区字段改为可编辑控件（标题、用户名、密码、网址、标签、备注），密码用 `PasswordBox` 并保留显示/隐藏按钮。
- 与进入详情时的快照比较，有差异才在卡片底部显示「保存修改 / 放弃修改」。
- 保存条固定在卡片底部，不随字段滚动，避免被长表单挤出可视区。
- 切换条目、搜索、上锁、关窗前自动保存；保存失败会阻止离开并显示错误，避免静默丢改动。
- 列表在保存后重建，标题等变更立即反映。

### 18.3 布局

主界面维持满宽布局（与 M2 交付一致），只有欢迎页居中。之前截图被裁切导致误判欢迎页偏右，已用 DWM 真实边框重新截图确认。

## 19. 环境适配（构建与运行）

排查“创建密码库失败”时遇到的两个与本机环境有关的问题，都已落到代码/脚本里：

| 现象 | 原因 | 处理 |
|---|---|---|
| 构建时报 `MakePri.exe` 退出代码 `0x80070005` | 该机器只允许未签名程序写项目目录，MakePri 写系统临时目录被拒 | `build.cmd` 把 `TMP`/`TEMP` 指向项目内 `.artifacts\temp` |
| 启动即崩溃，`Cannot locate resource from 'ms-appx:///Microsoft.UI.Xaml/Themes/themeresources.xaml'` | 为绕开 MakePri 曾关闭 PRI 生成，WinUI 主题资源索引随之缺失 | 恢复 PRI 生成；不能为了构建通过而关掉它 |
| 创建密码库报“无法在这个文件夹里创建文件” | 同一限制：程序写不了目标目录；文件对话框（系统进程）却能建 0 字节文件，容易误导 | 创建流程去掉所有删除/改名/`DeleteOnClose`，改为直接覆盖写入；失败信息指明具体文件和目录，并写 `startup.log` |

诊断用的启动日志（仅 Debug 构建）会记录：是否打包应用、临时目录/程序目录/用户目录是否可写，以及进程令牌的完整性级别。后续如果再加资源或本地化，需要重新评估 PRI 相关设置。

### 19.1 项目目录本身不可运行程序（重要）

在开发机上确认：把 `PwdMgr.App.exe` 放在 `D:\dev\pwdmgr-project\...\bin\...` 里运行时，进程被降为**低完整性**，无法写入任何普通目录（`D:\`、`D:\dev`、用户目录、`%TEMP%` 都拒绝）；把同一份产物复制到 `%LOCALAPPDATA%\PwdMgrApp` 后，进程是**中完整性**，选择器、创建密码库、写入 `D:\` 根目录全部正常。把系统记事本复制进项目目录同样无法启动。

原因在该目录的权限上：目录 DACL 里存在针对 Everyone 的拒绝条目和登录会话 SID 的授权（普通目录不会有），环境里有无法归属的过滤驱动（`ahflt`、`ClawFlt`），会把该目录下的可执行文件当作不可信程序处理。`ahflt` 疑似由游戏反作弊组件（腾讯 AntiCheatExpert）加载，`ClawFlt` 查不到公开资料，两者都难以只读方式确认归属；排查时也确认过：没有第三方杀软注册、没有域/Azure AD 管控、文件没有 MOTW 标记。

处理办法：**构建仍在该目录，运行请使用项目目录之外的副本**，例如：

```cmd
robocopy "src\PwdMgr.App\bin\x64\Debug\net8.0-windows10.0.19041.0\win-x64" "%LOCALAPPDATA%\PwdMgrApp" /E
"%LOCALAPPDATA%\PwdMgrApp\PwdMgr.App.exe"
```

这是开发机环境的限制，与应用代码无关。

## 21. 实施记录（M4）

M4 交付：密码生成器（独立窗口 + 密码框旁骰子）、剪贴板服务。

### 21.1 生成器（Core）

- `PasswordOptions` 记录长度与四个字符类别、是否排除易混淆字符（`I O l 0 1`）。
- `PasswordGenerator.Generate` 使用 `RandomNumberGenerator.GetInt32` 取随机数，没有取模偏差；先为每个启用的类别各取一个字符，再用合并字符池补足，最后 Fisher-Yates 洗牌，避免“某类字符固定出现在前几位”。
- 校验：长度 8–128、至少启用一类、长度不得小于启用的类别数；不满足时抛 `ArgumentException` / `ArgumentOutOfRangeException`。
- `EntropyBits` 按 `长度 × log2(候选池大小)` 估算，`DescribeStrength` 把比特数映射为「弱 / 中等 / 强 / 很强」。

### 21.2 生成器（界面）

- 独立窗口 `GeneratorWindow`：长度滑块（8–64）、五个勾选项、实时生成的密码与熵值、重新生成 / 复制。
- 选项通过 `AppShell.GeneratorOptions` 与主界面共享，密码框旁的“🎲”按钮按同一套选项生成；密码框已有内容时先弹确认再覆盖。
- 主界面工具栏新增“生成器”按钮与“清空剪贴板”按钮；快捷键 `Ctrl+N/G/F/L/S`。
- WinUI 的一个坑：在 XAML 里给 `Slider` 设置 `Minimum/Maximum` 会在运行时抛 `Failed to assign to property 'RangeBase.Minimum'`（即使写成 `8.0` 也一样），改为在代码里赋值后正常。

### 21.3 剪贴板

- `ClipboardService` 直接用 Win32 剪贴板 API：写入 `CF_UNICODETEXT` 的同时放入 `CanIncludeInClipboardHistory=0`、`CanUploadToCloudClipboard=0`、`ExcludeClipboardContentFromMonitorProcessing=1`，让 Win+V 历史与云剪贴板尽量忽略密码。
- 复制后启动 30 秒计时器；到点先读回剪贴板文本并比对 SHA-256，只有内容仍是本程序写进去的才清空，避免误删用户后来复制的数据。
- 手动“清空剪贴板”无条件清空；上锁时也会尝试清除本程序复制的内容。
- 打开剪贴板会失败（被其他程序占用）时最多重试 10 次、每次间隔 30 ms。

### 21.4 验证

- Core 单元测试新增 18 个：长度、字符类别覆盖、易混淆字符、非法参数、分布均匀性、熵值单调性。`dotnet` 直跑测试可执行文件：**62/62 通过**。
- UI 自动化端到端：新建草稿 → 点骰子 → 复制 → 剪贴板得到 20 位、字符集合法的密码；等待 30 秒后剪贴板为空；复制后手动写入别的内容，30 秒后不被误清；独立生成器窗口能打开、密码长度正确、复制内容与窗口一致。

## 22. 实施记录（M5）

M5 交付：备份、自检、从备份恢复、错误提示与互斥提示。

### 22.1 备份

- VaultSession.CreateBackupAsync(target)：先把未保存的修改落盘，再读取当前库、用当前钥匙解密校验、以原子方式写入目标并读回校验，返回备份大小。
- 拒绝把备份写到库文件本身；目标已存在时直接覆盖（文件对话框已经确认过覆盖）。
- 界面：工具栏“更多 → 创建备份…”，默认文件名 库名-备份-yyyyMMdd-HHmm.pwdb，成功后 InfoBar 显示大小与路径，并提醒同时保管钥匙文件。

### 22.2 自检

- VaultSession.VerifyAsync()：重新从磁盘读取密码库，用当前钥匙解密，核对库标识与内存会话一致，再重新加载钥匙文件核对 keyId，返回有效/回收站条目数与文件大小。
- 任何一步失败都抛带错误码的 VaultException：篡改密文 → DecryptionFailed，截断 → FileCorrupted，钥匙换了 → KeyMismatch。
- 界面：“更多 → 检查密码库”，结果以 InfoBar 显示“校验通过：有效条目 N 条，回收站 M 条，文件 X KB”。

### 22.3 从备份恢复

- VaultSession.RestoreFromFileAsync(vault, key, backup)：用磁盘上的钥匙解密备份（不是同一个库则报 KeyMismatch），原子写回库文件，旧版本自动保留为 .bak，随后读回校验。
- 界面：“更多 → 从备份恢复…”→ 选择备份 → 确认对话框 → 恢复成功后 AppShell.RestartAsync（销毁会话、重新打开、重新进入主界面），并显示一次性提示“已从备份恢复”。
- 之所以做成“重新打开会话”，是因为内存中的文档在覆盖后已经过期，重建会话比原地替换状态更不容易出错。

### 22.4 错误提示与互斥

- 错误码到中文提示的映射统一在 VaultException.Describe，界面只展示 ex.Message；VaultBusy 的提示是“这个密码库正在被另一个窗口使用。”
- 备份/恢复失败分别包成“备份失败：…”“恢复失败：…”，不会只显示异常类型。

### 22.5 验证

- Core 单元测试新增 9 个（共 **71** 个）：备份能打开、备份前自动保存、同路径拒绝、校验计数、篡改/截断检测、恢复回被删条目、恢复别库备份报 KeyMismatch、备份缺失报 VaultFileNotFound。
- UI 自动化：检查密码库显示“校验通过…”；创建备份生成文件且显示“备份已保存”；删除条目后列表消失、回收站可见。

## 24. 拖拽打开（用户反馈）

### 24.1 行为

- 欢迎页：把 .pwdb 拖进窗口 → 直接跳到“打开密码库”页并填好路径；只拖 .key → 顶部提示“请先拖入密码库文件，再拖入钥匙文件。”
- 打开页：可以分别拖入密码库与钥匙文件；拖密码库时如果同目录存在同名 .key 会自动填上；**没有密码库时先拖钥匙会提示必须先有密码库**。
- 一次拖入两个文件也可以：按扩展名分别归类，先应用密码库再应用钥匙，所以两个一起拖不会被“先钥匙”规则挡住。
- 其它类型（图片、文件夹、多个同类文件里的多余项）会被忽略；一个可用文件都没有时提示“只支持拖入 .pwdb 密码库文件或 .key 钥匙文件。”

### 24.2 实现

- FileDropHelper：判断拖放内容是否含存储项（StandardDataFormats.StorageItems）、在 DragOver 里设置 AcceptedOperation = Copy 与拖拽提示文字、在 Drop 里把 StorageFile 按扩展名分成密码库/钥匙两类，同类只取第一个。
- 页面用 AllowDrop="True" 的根 Grid 作为投放面，并用 AddHandler(DragOverEvent/DropEvent, ..., handledEventsToo: true) 注册，避免子元素（输入框等）把事件标记为已处理后页面收不到。
- 投放面必须设置 `Background="Transparent"`：WinUI 里没有 Background 的面板不参与命中测试，结果只有按钮等有视觉的子控件能接住拖放、空白区域接不到（首版踩过这个坑）。
- 欢迎页与打开页都加了提示文字；欢迎页额外用顶部 InfoBar 显示“先钥匙”之类的错误。

### 24.3 已知限制

- 程序以管理员身份运行时，从普通权限的资源管理器拖文件进来会被 Windows 的 UIPI 拦截（提权进程不接受低权限进程的拖放），这是系统限制。
- 开发沙箱里资源管理器的 UI 自动化项目读不到、无法自动模拟拖拽，本功能需在正常桌面上手工验证。

## 27. 生成器支持自定义字符

需求：允许在生成规则里额外加入自定义字符。

- PasswordOptions 新增 CustomCharacters（默认空）。PasswordGenerator 把它当成第五个字符池：去重、忽略控制字符，但**不受“排除易混字符”影响**（用户主动写的 I/O/l/0/1 会保留）。
- 因为每个启用的池至少取一个字符，所以只要填了自定义字符，生成的密码里一定至少出现一个；池之间允许重叠，熵值按去重后的并集计算，避免高估。
- 全部内置类别都取消勾选、只填自定义字符时也能生成（此时密码完全由自定义字符组成）。
- 界面：生成器窗口新增“自定义字符”输入框（最长 64 字符，提示“填了就保证至少出现一个”），改动同样遵循“不立即重算、点生成才应用”。窗口高度相应调整为 560×740，最小 460×660。
- 测试：新增 4 个用例（必含自定义字符、仅自定义字符、去重、易混字符不被过滤），Core 测试共 **75** 个通过。
- 验证：UI 自动化——改自定义字符后密码不变；点“生成”后新密码包含 ★ 或 ※，长度仍是设置的 30。

### 27.1 自定义字符排除空格

按反馈补充：自定义字符里的空白字符（普通空格、制表符、全角空格等）与控制字符一律丢弃，不再进入字符池；提示文字也写明“空格会被忽略”。新增用例 Generate_CustomCharactersExcludeWhitespace 验证 " A\tB　C " 只保留 ABC 且生成的密码里没有空白，Core 测试共 **76** 个通过。

## 29. 深色主题与跟随系统开关

### 29.1 行为

- 默认**跟随系统**（沿用原有行为，Mica 背景生效）。
- 欢迎页右下角、主界面工具栏最右各有一个齿轮按钮，菜单为“跟随系统 / 浅色 / 深色”，当前项带勾选。
- 选择后立即应用到所有已打开窗口（含密码生成器窗口），并写入 %LOCALAPPDATA%\PwdMgr\settings.json，下次启动沿用。
- 强制浅色/深色时**关闭 Mica**、改用对应的纯色背景：Mica 的配色来自系统，强制主题时会对不上内容。

### 29.2 实现

- AppSettings：Theme 枚举（System/Light/Dark），JSON 序列化（枚举写成字符串），读写失败只记日志、不影响主流程。
- ThemeService：维护已登记窗口的弱引用列表，Apply 时给每个窗口的根元素设置 RequestedTheme（Application.RequestedTheme 只在启动时生效，不能用于运行时切换）。
- MainWindow.ApplyBackdropForTheme：跟随系统时恢复 Mica 并清空根背景；强制主题时移除 SystemBackdrop 并设置 #FFF3F3F3 / #FF202020 纯色。
- 生成器窗口的根 Grid 加了 ApplicationPageBackgroundThemeBrush 背景，切换主题时随之变化。

### 29.3 验证

- UI 自动化：点齿轮 → 选“深色” → 界面整体变深色；再选“浅色” → 变浅色（截图核对）。
- 设置写入在开发沙箱里会失败（当前进程是低完整性，%LOCALAPPDATA% 不可写），日志会记录“保存设置失败”，但不影响切换；在正常权限下（用户机器）可正常保存，重启后沿用。

### 29.4 修正：对话框与标题栏按钮不跟随主题

反馈发现两处遗漏：

- **ContentDialog 仍是浅色**：对话框不会继承窗口根元素的 RequestedTheme。现在创建对话框后统一调用 ThemeService.ApplyToDialog(dialog)（设置 RequestedTheme），创建密码库成功提示、删除确认、彻底删除、清空回收站四个对话框都覆盖到。
- **标题栏的最小化/最大化/关闭仍是系统配色**：自定义标题栏下这些按钮由系统绘制。现在 MainWindow.ApplyTitleBarTheme 设置 AppWindow.TitleBar.PreferredTheme（跟随系统时为 UseDefaultAppMode），并同步按钮前景/悬停/按下颜色作为兜底。
- 验证：系统浅色、程序切深色后，删除确认框整体变深；标题栏三个按钮变成白色图标。

## 30. 密码强度提示 + 上锁后清空钥匙路径

### 30.1 密码框下方的强度提示

- Core 新增 PasswordStrength.Evaluate：按出现过的字符类别粗算候选池（小写 26 / 大写 26 / 数字 10 / 符号 33 / 其它 100），熵值 = 长度 × log2(池大小)，再用与生成器一致的口径给出「弱 / 中等 / 强 / 很强」。
- 界面在密码框下方显示“强度：很强（20 位，约 131 比特）”，颜色用主题色区分：弱=红、中=橙、强/很强=绿（App.xaml 里三个带 ThemeResource 的 Style，深色主题同样适用）。
- 切换条目、新建草稿、手动改密码、用骰子生成时都会刷新。
- 测试：新增 10 个用例（空密码、短密码偏弱、长混合密码很强、增加字符类别提高熵值、中文按其它类别计算、标签映射），Core 测试共 **86** 个通过。

### 30.2 上锁后清空钥匙路径

- 上锁后跳转“打开密码库”页时只带密码库路径；UnlockNavigationArgs.SuggestKey=false，钥匙路径保持为空，必须重新选择或输入钥匙文件。“打开”按钮在钥匙为空时不可用。
- 其它入口（拖入文件、命令行启动失败回退）仍然会顺手填上同名 .key，这两处显式传 suggestKey: true。
- 验证：UI 自动化上锁后读取两个输入框——VAULT_AFTER_LOCK=…vault.pwdb、KEY_AFTER_LOCK=（空）、KEY_CLEARED=True。
- 顺手修了“上锁”按钮缺少无障碍名称的问题（AutomationProperties.Name="上锁"）。
